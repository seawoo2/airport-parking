# 데이터 수집 코드 작성 전 준비사항

## 목표

인천공항 주차 현황 데이터를 안정적으로 수집하고 PostgreSQL에 저장할 수 있도록, 구현 전에 결정할 사항과 작업 순서를 정리합니다. 현재 로컬 Docker PostgreSQL과 Python 연결은 완료된 상태입니다. 클라우드 배포와 주기 실행은 수집 프로그램이 로컬에서 검증된 뒤 진행합니다.

## 현재 준비된 환경

- Python 3.13 및 `uv`
- `psycopg`와 `python-dotenv`
- 로컬 Docker PostgreSQL 연결
- 코드 영역: `src/airport_parking/collectors/`
- 데이터 저장 위치: 로컬 DB; 원본 응답 파일이 필요한 경우 `data/raw/`

## 확인된 공식 데이터 출처와 1차 범위

- 공식 출처: [공공데이터포털 — 인천국제공항공사_주차 정보](https://www.data.go.kr/data/15095047/openapi.do)
- 엔드포인트: `https://apis.data.go.kr/B551177/StatusOfParking/getTrackingParking`
- 범위: T1·T2 주차구역별 현황. 단기·장기 주차장 구분은 응답의 `floor` 값을 사용합니다.
- 인증: 공공데이터포털 활용신청 후 받은 `serviceKey`가 필요합니다. 개발·운영 단계 모두 자동승인으로 안내됩니다.
- 이용 조건: 무료, 이용허락범위 제한 없음. 개발 계정 하루 1,000회 호출 한도입니다.
- 요청: `serviceKey`, `numOfRows`, `pageNo` 필수, `type=json` 지정 가능.
- 응답: `floor`(주차구역명), `parking`(주차 대수), `parkingarea`(총 주차면수), `datetm`(주차 현황 갱신 시각), `totalCount`, `resultCode`.
- `parkingarea=0`은 제공처가 **미운영**으로 정의합니다. 혼잡률 계산 대상에서 제외해야 합니다.
- 조회 당일 데이터만 제공하므로 과거 학습 데이터를 얻으려면 주기적인 수집이 필요합니다.

공식 문서의 예시 시각은 `20211103162024.804`입니다. 1차 구현에서는 이를 한국시간으로 해석해 저장하지만, 실제 응답의 시간대와 항목 구조는 서비스키로 첫 호출을 한 뒤 확인해야 합니다. 안정적인 주차장 코드는 명세에 없어 `floor` 문자열을 식별자로 사용합니다. 제공처가 이름을 변경하면 별도 주차장으로 저장될 수 있습니다.

## 구현 전에 결정할 항목

### 1. 수집 목표와 범위

- [ ] 첫 버전에 수집할 주차장 범위를 정합니다. 예: 여객터미널 주차장, 장기주차장, 예약주차장
- [ ] 예측에 사용할 목표값을 정합니다. 예: 주차 가능 대수, 주차된 대수, 혼잡률
- [ ] 필요한 수집 주기를 정합니다. API 갱신 주기와 예측 시간 간격을 함께 고려합니다.
- [ ] 과거 데이터도 필요한지 확인합니다. 실시간 API만 제공한다면 모델 학습용 이력이 쌓일 때까지 수집을 계속해야 합니다.

### 2. 데이터 제공처 확인

- [ ] 공식 API 또는 공공데이터 출처를 확정합니다.
- [ ] 인증키 발급 절차, 호출 한도, 이용료, 이용약관 및 출처 표시 조건을 확인합니다.
- [ ] 응답 예시와 문서를 확보하고, 실제 필드명·자료형·단위·갱신 시각을 확인합니다.
- [ ] 오류 응답, 데이터 누락, 점검 시간, 호출 제한 시 동작을 확인합니다.
- [ ] API가 반환하는 시각이 관측 시각인지 응답 생성 시각인지 구분합니다.

> 데이터 제공처와 API 문서는 아직 이 문서에서 확정하지 않았습니다. 구현 전에 공식 출처를 기준으로 확인합니다.

### 3. 저장할 데이터와 식별 기준

- [ ] 원본 응답을 보관할지 결정합니다. 원본 보관은 파싱 로직 변경 후 재처리에 유용합니다.
- [ ] 정규화할 필드를 정합니다. 최소 후보: 주차장 ID/명, 전체 주차면, 주차 대수 또는 잔여 면수, 제공처 관측 시각, 수집 시각.
- [ ] 주차장 식별자는 이름보다 제공처의 안정적인 코드가 있는지 우선 확인합니다.
- [ ] 결측값, 0, 음수, 범위 초과를 어떻게 처리할지 정합니다. 원본값을 임의로 보정하지 않습니다.
- [ ] 중복 수집 판정 기준을 정합니다. 예: 제공처 + 주차장 ID + 관측 시각 조합에 고유 제약을 둡니다.
- [ ] 모든 시각의 의미와 시간대를 정합니다. 국내 관측 시각은 `Asia/Seoul` 기준을 명시하고 DB 저장 기준을 일관되게 유지합니다.

### 4. 수집 및 저장 동작

- [ ] HTTP 연결·응답 타임아웃을 둡니다.
- [ ] 일시 오류에 제한된 재시도와 대기 시간을 적용합니다. 인증 오류나 잘못된 요청은 무한 재시도하지 않습니다.
- [ ] API 호출, 응답 파싱, 유효성 확인, DB 저장을 분리합니다.
- [ ] 여러 주차장 데이터를 저장할 때 트랜잭션 범위와 일부 실패 처리 방식을 정합니다.
- [ ] 같은 데이터를 다시 받아도 중복 행이 생기지 않도록 upsert 또는 고유 제약 기반 저장 방식을 선택합니다.
- [ ] 로그에 실행 시각, 요청 결과, 처리 건수, 실패 원인을 남기되 인증키와 비밀번호는 기록하지 않습니다.
- [ ] API 응답이 비어 있거나 스키마가 바뀐 경우 조용히 성공 처리하지 않고 알아볼 수 있게 실패시킵니다.

### 5. 설정과 비밀정보

- [ ] API 키와 DB 접속 정보는 코드에 직접 쓰지 않고 환경 변수로 읽습니다.
- [ ] 로컬 값은 `.env`에 두고 Git에 커밋하지 않습니다.
- [ ] `.env.example`에는 변수명과 설명만 기록하고 실제 비밀 값은 넣지 않습니다.
- [ ] 개발 DB와 운영 DB 설정을 분리하고, 클라우드 배포 시 플랫폼 비밀 변수로 옮깁니다.

## 권장 데이터 흐름

```text
공식 API
  → 응답 수집
  → 원본/수집 메타데이터 기록(선택)
  → 필드 정규화 및 유효성 확인
  → 중복 방지 기준으로 PostgreSQL 저장
  → 처리 건수와 오류 로그
```

수집기 코드는 API 통신을 담당하고, 전처리 코드는 응답 해석과 정규화를 담당하며, DB 저장 코드는 별도 모듈로 분리하는 구성을 권장합니다. 이렇게 하면 API 제공처나 저장 방식을 바꿀 때 수정 범위를 줄일 수 있습니다.

## 진행 순서

1. 공식 데이터 제공처와 인증·호출 조건을 확인합니다.
2. API 응답 샘플을 확보하고 필요한 필드와 시각 의미를 정리합니다.
3. 수집 범위, 주기, 중복 기준, 결측 처리 규칙을 확정합니다.
4. DB 테이블 초안을 작성하고 고유 키 및 인덱스를 정합니다.
5. 환경 변수와 `.env.example`을 준비합니다.
6. API 요청과 응답 파싱을 DB 저장과 분리해 작은 단위로 구현합니다.
7. 저장 결과를 확인하고 재실행해도 중복되지 않는지 검증합니다.
8. 로컬에서 안정적으로 동작한 뒤에 클라우드 실행 환경과 스케줄을 결정합니다.

- [ ] 응답 필드, 시간대, 데이터 단위가 문서화되어 있습니다.

- [ ] 같은 관측 데이터를 다시 처리해도 중복 행이 생기지 않습니다.
- [ ] API 실패와 파싱 실패를 로그에서 구분할 수 있습니다.
- [ ] 수집 주기와 재시도 동작을 로컬에서 확인한 뒤 클라우드 배포를 시작합니다.
